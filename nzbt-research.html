The runtime thesis and the research behind it

The central question is whether an audio runtime can realize discrete changes over a non-zero interval, taking more responsibility for transitions that developers normally implement separately. Parameters, algorithms, voice allocation, graph topology and model changes belong to that scope. The listening demo covers one filter replacement.

How the proposal developed

The original plan groups three mechanisms: parameter trajectories, concurrent output crossfading and explicit state projection. It considers three runtime arrangements: an external dual-graph wrapper, a state-transfer interface and a render-ahead pipeline. These are ways of realizing a transition, rather than a promise that the same technique fits every process.

The later addendum introduces signal, copy and sample fallbacks. Their time-aligned outputs are blended with nonnegative weights summing to one. An application-specific objective would choose the feasible paths and weights using transition error, available latency, state uncertainty and processing cost. Feedforward prepares a requested change; feedback can adjust the result, with its own delay accounted for.

These classifications operate at different levels. Parameter interpolation and state projection describe transformations inside a process; signal, copy and sample describe candidate ways of sustaining its audible output. State access can help a copy path; lack of it does not automatically rule out an acceptable output bridge.

What was challenged

The original phase-opposition example demonstrates cancellation for a particular crossfade. It does not, by itself, prove the stated impossibility for every possible external operator. The later state-space derivation shows that a limited pre-roll can leave historical state error. That does not establish an audible discontinuity in the combined output or a categorical failure whenever a memory time constant exceeds the horizon.

The reports also claim that smooth weights guarantee amplitude and slope continuity, that short-memory IIR systems reach exactly zero state error, and that three paths necessarily triple compute cost. Those statements need conditions or measurement. They should not be treated as established properties of this implementation.

What the current demo establishes

The browser example evaluates a stated amplitude-and-slope tracking objective and actually optimizes path weights. Its longer-history reference diagnoses output mismatch independently; it is not supplied to the controller. Its target favors a particular smooth transition and is not a validated perceptual metric. It performs offline calculations, uses extra iterations for the three-path solver, and supplies neither real-time performance evidence nor a universal guarantee.

What remains part of the thesis

The runtime contract, developer burden, continuity levels, graph and voice changes, feedback memory, intentional transients, neural context and conditioning, resource deadlines and failure criteria remain substantive parts of NZBT. The perceptual and buffering argument modifies the constraints under which those questions are judged. It does not replace them.

Executive Summary and Verdict

The Non-Zero Boundary Transition (NZBT) hypothesis addresses a fundamental systemic tension in digital audio engineering: the contradiction between continuous physical acoustics and discrete computational execution. In digital signal processing (DSP) runtimes, computational state mutations—including parameter updates, algorithm swaps, voice reallocations, and graph topology modifications—occur at discrete sample boundaries. To prevent these step changes from inducing audible transient artifacts such as clicks, pops, and zipper noise, audio developers must manually embed temporal transition logic within their DSP algorithms1. The NZBT concept asks whether this engineering burden can be shifted downward into an underlying runtime layer that guarantees that discrete computational state updates manifest externally across a non-zero temporal interval .

Verdict: Useful recombination of known mechanisms

The NZBT hypothesis represents a useful recombination of known mechanisms spanning industrial control theory ("bumpless transfer"), declarative computer music runtimes (SuperCollider NodeProxy crossfading), and time-varying DSP state-space transformations3. While the hypothesis provides a rigorous unifying lens for framing computational state boundaries, it fails as a universal bottom-layer invariant for arbitrary black-box audio processes.
Although a runtime layer can enforce amplitude () or derivative () continuity across arbitrary black-box outputs via speculatively executed crossfades5, it cannot universally guarantee phase, spectral, or dynamic response continuity without domain-specific state-space knowledge3. For stateful systems containing internal feedback—such as infinite impulse response (IIR) filters, physical models, and recirculating delay networks—transition management must occur inside the internal state topology rather than at an external output boundary3. Consequently, NZBT cannot eliminate developer complexity universally; attempting to enforce it as an opaque runtime invariant introduces destructive phase cancellation, computational load spikes, latency penalties, and the unintended smoothing of deliberate musical transients6.

The informal mathematical starting point correctly highlights the temporal extension requirement, but the path formulation is valid only when forms a connected topological manifold2. 2. Taxonomy of Prior Art

Managing discrete state changes without introducing transient artifacts has been independently investigated across industrial control theory, computer music languages, digital signal processing, host plugin architectures, and neural synthesis pipelines.

Industrial Control Theory: "Bumpless Transfer"

In control engineering, switching between manual and automatic control modes or swapping active dynamic controllers in proportional-integral-derivative (PID) loops presents an identical structural challenge4. A step change in controller output can cause physical actuator wear or mechanical instability4. Control theory resolves this via Bumpless Transfer (BT) algorithms4. When switching controllers, the offline controller's internal integral state is updated via a tracking observer to match the online controller's current output prior to handoff4. Modern control synthesis extends this to switched linear systems using Anti-Disturbance Bumpless Transfer (ADBT) compensators to enforce smooth transitions across discrete control modes7.

Declarative Computer Music Runtimes

Computer music environments provide declarative mechanisms for dynamic graph mutation. SuperCollider's Just-In-Time Library (JITLib) implements proxy-based graph substitution via NodeProxy and Ndef abstractions5. When an audio-producing source assigned to an Ndef is replaced, the runtime automatically executes an overlapping crossfade according to a specified fadeTime5. The engine spawns the target synth node, ramps its gain from 0 to 1, ramps the old synth node's gain from 1 to 0, and frees the old node upon completion5. Languages such as Csound, Pure Data (Pd), and ChucK provide high-level dynamic crossfading primitives, though responsibility for maintaining internal DSP filter memory across swaps remains with the user1.

Digital Signal Processing and Time-Varying Filters

In traditional DSP literature, preventing parameter transition artifacts is categorized under dezippering and click-free switching2. Early research prioritized low-pass filtering and exponential interpolation of control-rate parameters2. For time-varying digital filters, Aaron Wishnick established that State Variable Filter (SVF) structures discretized via trapezoidal integration (the bilinear transform) maintain stability and continuous energy bounds under sample-rate parameter changes because their state updates explicitly account for continuous energy flow through integrator stages10. For fractional delay lines, Zölzer and Stilson developed lossless, click-free delay-loop interpolation techniques to adjust delay lengths without introducing pitch glitches or amplitude jumps8.

Host Audio Runtimes and Plugin Frameworks

Plugin interfaces (VST3, CLAP, LV2) and browser audio runtimes (Web Audio API) handle parameter automation via sample-accurate event queues19. The Web Audio API exposes scheduled timeline commands such as linearRampToValueAtTime() and setTargetAtTime() on AudioParam objects19. However, these frameworks maintain a rigid separation: the host guarantees sample-accurate event delivery, but delegates DSP transition realization entirely to the individual plugin or AudioWorkletProcessor19.

6. Failure Modes of "Crossfade Everything"

Relying on output-level crossfading as a universal solution breaks down across common DSP topologies:

  • Phase Cancellation and Comb Filtering: Crossfading two uncorrelated or out-of-phase periodic signals (e.g., unsynchronized oscillators or slightly delayed acoustic signals) causes destructive interference, resulting in amplitude drops or comb filtering8.
  • Stateful Feedback Systems: In recursive topologies (e.g., feedback delay networks, physical waveguides, and resonant filters), energy recirculates within internal delay vectors3. Crossfading at the output leaves the active feedback loop unmanaged; switching the source process cuts off internal recirculation abruptly, causing unnatural decay tails or state accumulation glitches3.
  • Nonlinear Dynamic Processors: Dynamic processors (e.g., compressors, limiters, and envelope followers) track signal energy using non-linear memory states. Crossfading two dynamic processes scales down intermediate signal levels (), distorting sidechain detection and causing threshold release chatter4.
  • Compute Exhaustion: Dual-graph execution ( and running concurrently) during crossfades doubles computational overhead. For compute-heavy processes (e.g., neural vocoders or dense convolution reverbs), this causes processing spikes and real-time audio dropouts6.
  • Masking Intentional Transients: Musically valid instantaneous transitions (e.g., drum attacks, hard synthesizer sync, square waves, and granular synthesis) rely on sharp sample-to-sample steps. An absolute runtime invariant forcing softens intended transients, degrading rhythmic sharpness9.

7. Neural and AI Audio Implications

Modern deep-learning audio architectures alter traditional callback-driven DSP paradigms, introducing distinct structural considerations for NZBT6.

Context Caching and Streaming Inference

Neural architectures (e.g., RAVE, EnCodec, DDSP, and SoundStream) rely on temporal convolutions or autoregressive transformer layers6. Because convolutional layers possess broad receptive fields, processing isolated audio chunks introduces frame-edge boundary artifacts6. To achieve real-time streaming, neural engines use causal streaming convolutions with cached receptive field states6. The internal state (activation memory from preceding frames) is persisted across chunk evaluations6. Swapping neural models mid-stream corrupts this activation cache, generating severe transient impulse bursts6.

Dynamic Conditioning Trajectories

When conditioning vectors (e.g., latent space embeddings, timbre parameters, or fundamental frequency tracks) change mid-stream, applying step changes to Feature-wise Linear Modulation (FiLM) layers causes synthesis artifacts21. FiLM layers scale and shift intermediate feature maps:

Asynchronous Execution and Render-Ahead

Neural audio models typically execute asynchronously from hardware buffer clocks due to variable inference latency6. Engines maintain a speculative lookahead queue (e.g., 20–50 ms) to absorb processing jitter6. This render-ahead architecture provides a natural framework for NZBT: because future output frames are rendered in advance, the runtime has lookahead time to detect upstream state updates, pre-warm initial conditions for new neural instances, and execute overlapping crossfades prior to hardware playback6.

  3. Non-Causal Render-Ahead Pipeline: Inserts an intentional lookahead buffer between control event input and audio rendering6. Control events are processed ahead of real-time playback, giving the engine time to handle pre-roll, state estimation, and windowed overlap-add transitions without introducing audio dropouts6.

10. Falsification Criteria

The generalized NZBT abstraction should be considered invalid or counterproductive if experimental evaluation yields any of the following quantitative outcomes:

  1. Phase Notch Failure: Output-level crossfading across out-of-phase nodes introduces an amplitude drop exceeding within the transition window 8.
  2. Computational Overhead Threshold: The CPU cost of executing dual-graph speculative nodes during transitions increases total render-thread execution time by , causing real-time buffer underruns6.
  3. Latency Penalty Boundary: Guaranteeing click-free transitions for arbitrary black-box nodes requires an introduced lookahead latency , exceeding acceptable real-time live-performance limits26.
  4. Developer Complexity Shift Failure: Exposing the necessary state-export and projection interfaces forces audio developers to write more boilerplate code than standard parameter smoothing routines, failing the primary goal of reducing developer burden3.

Systemic Conclusions

The Non-Zero Boundary Transition hypothesis provides a structured framework for conceptualizing state transition dynamics across real-time audio systems. However, it cannot serve as an opaque, universal infrastructure layer that hides state transitions entirely3. For continuous parameters, standard DSP smoothing filters remain the most computationally efficient solution2. For structural graph substitutions, declarative crossfading runtimes (e.g., SuperCollider's NodeProxy) successfully isolate output transitions5. For stateful DSP topologies, transition logic must remain aware of internal system state3. Attempting to abstract state transitions entirely into an external runtime layer either degrades audio quality through phase cancellation or shifts state-management complexity into host-node contract negotiations3.
